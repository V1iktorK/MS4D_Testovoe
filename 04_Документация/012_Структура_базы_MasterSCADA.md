# 012. Структура базы проекта MasterSCADA 4D

**Назначение.** Зафиксировать, как в базе MasterSCADA 4D хранятся элемент, параметры, программа, окно,
привязки и конвертеры. Документ составлен при проверке собранного комплекта: нужно было убедиться, что
в файлах сдачи действительно есть всё, что заявлено в документах, и что ничего не потерялось при сборке.

**Стенд:** MasterSCADA 4D 1.3.10.37086, файлы комплекта открывались копиями; база читалась клиентом
Firebird 2.5 из поставки среды (`fbembed.dll`, встроенный сервер, монопольный доступ).

---

## 1. Файл проекта — это папка, а не файл

Проект (и библиотека) на диске — **папка** из трёх частей:

| Часть | Что это |
|---|---|
| `info.xml` | паспорт проекта (`PersistProjectInfo`): GUID, имя, тип (`MasterSCADA.Library.HMI` / `MasterSCADA.Project.HMI`), дата изменения, версия базы |
| `<имя>.fdb` | собственно база: Firebird 2.5, диалект 3, кодировка UTF8 |
| `Queries\` | папка запросов, которую среда создаёт рядом с базой |

Одиночный `.fdb` среда как проект не открывает — ей нужен `info.xml`. Библиотека лежит в папке с
расширением имени `*.ms4proj`.

## 2. Таблицы

| Таблица | Содержимое |
|---|---|
| `ITEMS` | все объекты базы: `ITEMID`, `TYPEID` (тип из `TYPES`) |
| `TYPES` | словарь типов: `TYPEID`, `KIND` (1 — объект, 2 — связь, 3 — свойство), `NAME`, `VERSION` |
| `PROPSNUM`, `PROPSSTR`, `PROPSBLOB` | значения свойств: `ITEMID`, `TYPEID` свойства, `VERSION`, `VALUE` |
| `LINKS` | связи: `SOURCEID`, `TARGETID`, `TYPEID` связи |
| `SYSPROPS` | служебные параметры базы (имя — значение) |

Два практических правила, которые сэкономили время:

1. **Идентификаторы типов в разных базах разные.** Один и тот же тип (`MasterSCADA.Attribute`) в
   библиотеке и в шаблоне проекта имеет разные `TYPEID`. Искать тип нужно по `TYPES.NAME`, а не по числу.
2. `TYPES` — не справочник всех типов среды, а **словарь фактически использованных** в этой базе.

## 3. Элемент

```
MasterSCADA.Object                     объект-элемент
├── Item (DefId = 3)                   узел элемента в дереве
├── MasterSCADA.Attribute × N          параметры элемента
└── MasterSCADA.Resources (DefId = 1)  ресурсы
    ├── Program.Programs (2)           программы
    ├── View.ViewDeclarationInObjects (3)  объявления окон
    └── AlarmUsages (4)                сообщения
```

Параметр `MasterSCADA.Attribute` — это «параметр элемента» с точки зрения пользователя. Внутри он
состоит из свойств `MasterSCADA.Var.Type` (BOOL / INT / DINT / REAL / STRING / TIME) и
`MasterSCADA.Var.InitialValue` (начальное значение). **Направление параметра** хранится не на нём, а на
парном узле `MasterSCADA.Program.Param` — свойство `MasterSCADA.Var.AccessType`: 0 — вход, 1 — выход,
2 — вход-выход. Связь параметра с программой — линк `MasterSCADA.ReadValue`.

## 4. Программа

Текст ST лежит в свойстве `Designer.Font.Text` объекта `MasterSCADA.Program.POUAlgoritm.ST` — в блобе
**UTF-16LE без BOM**. Если читать блоб как однобайтовый текст, кириллица и структура выглядят мусором:
это первое, на что стоит обращать внимание при разборе чужой базы.

## 5. Окно

```
MasterSCADA.View.Screen               окно
├── ScreenParameters (2)              параметры окна
├── ScreenElements (3)                графические объекты
├── Connections (4)                   привязки
├── Events (5)                        события (клик мыши, клавиатура)
├── Resources (6)                     ресурсы окна
└── Triggers (7)                      условия/триггеры
```

* Графический объект — `View.ViewUsage` + линк `Reference` на `View.ViewType`; тип определяется по
  `SubTypeName` (например `Group`, `Text`, `Indicator`, `Button`, `Trend`, `Table`).
* Геометрия — свойства `Designer.Layout.X / Y / Z / Width / Height`.
* **Привязка** — объект `View.Connection` со свойствами `Scheme.InLink` и `Scheme.OutLink`. Имя связи
  строится по схеме `LParameters_<Параметр>$Elements_<Объект>_Parameters_<Свойство>`; по нему видно,
  к какому параметру элемента и к какому свойству объекта относится связь.

## 6. Конвертеры

Конвертер привязки — свойство `MasterSCADA.Var.Convertation` объекта `View.Connection`, блоб
**UTF-16LE** с JSON. Типы: `ConverterType = 1` — дискретный (перечислитель «значение → цвет, текст»),
`ConverterType = 2` — линейный/пороговый (диапазон входного значения → цвет). Дискретный конвертер
строится таблицей пар, первая строка — значение `False`.

## 7. События и команды

* Команда кнопки — `View.MouseEvent` → действие `View.Action.SetParameter`; других путей записи в
  параметр из окна нет (это же требование зафиксировано в `10_Общие_соглашения.md`).
* Переход между окнами — действие `View.Action.OpenDialog`, цель задаётся `ViewDeclarationUsage`
  через `Scheme.InLink`.

## 8. Тренд и журнал

* Перья тренда — параметр `PensData` с `Var.Type = 'Pens'`: массив `TrendPens`, элементы — структура
  `TrendPen` (19 полей, в том числе тип значения).
* Журнал — `View.JournalType` «Журнал»; в шаблоне библиотеки журнальных таблиц нет: сохранение проекта
  средой не создаёт в базе обязательных записей журнала (`TRANS_LOG` пуст, `LastTransId = 1`).

## 9. Чем это использовалось

Проверка полноты комплекта: пересчёт элементов, параметров, окон, привязок, конвертеров и
переопределённых значений экземпляров прямо в базе — вместо ручного просмотра дерева из 87 окон.
Результат сверки: 8 элементов, 2 368 параметров элемента (2 541 запись `Attribute` вместе со
служебными группами), 87 окон ПБЭ, 3 546 использований окон, 3 600 привязок, 816 конвертеров
(из них 156 — линейные/пороговые), 55 экземпляров в проекте разработки с 303 настроенными значениями.

## 10. Оговорки

* Прямой SQL-доступ к базам поставки среды (`DEFAULT.FDB`, `MasterSCADA.Library.HMI.fdb`, `Examples.fdb`)
  закрыт правами владельца. Сведения о типах и подписях брались из XML-реестров установки — см.
  `010_Сверка_со_средой_1.3.10.37086.md`.
* Формат поля `Значение` в структуре пера тренда (`REF_TO`) подтверждён не полностью: перья заданы
  параметром `PensData`, приёмка перьев — ручная операция в среде.
