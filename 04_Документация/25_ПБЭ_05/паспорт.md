## 2. Назначение

Универсальный тип для систем кондиционирования VRF трёх производителей. Один экземпляр охватывает **всё кондиционирование корпуса**: все наружные и внутренние блоки. Обеспечивает отображение состояния блоков, управление отдельным блоком, тренды и архивирование.

> **Принципиальное отличие от всех остальных ПБЭ комплекта.** ПБЭ № 1–4, 6–8 построены по схеме «один экземпляр — одна установка». Здесь **один экземпляр — вся система корпуса**, внутри которой десятки блоков, каждый со своими параметрами. Это меняет всю конструкцию: не добавляется один блок параметров, а размножается по числу блоков.

## 5. Ключевое проектное решение: объём параметров

### 5.1. Измерение задачи

Каждому блоку нужны «собственные параметры». По ТЗ параметры **одного** внутреннего блока — **семь**: включение, уставка, температура помещения, режим, скорость вентилятора, ошибка, защита.

Прямой расчёт числа параметров **одного экземпляра**:

| Экземпляр | Наружные (× 8 параметров) | Внутренние (× 7 параметров) | Итого блоков | + общие/шлюз/индексы | **Всего** |
|---|---|---|---|---|---|
| LG, корпус 3 | 7 × 8 = 56 | 55 × 7 = **385** | 441 | ~40 | **≈ 481** |
| Electrolux, корпус 8 | 5 × 8 = 40 | 62 × 7 = **434** | 474 | ~40 | **≈ 514** |
| **MDV, корпус 22** | 7 × 8 = 56 | 66 × 7 = **462** | 518 | ~40 | **≈ 558** |

**Вывод: один экземпляр ПБЭ № 5 требует ≈ 480…560 параметров** — больше, чем **любой другой ПБЭ комплекта** (у ПБЭ № 1 ≈ 306).

### 5.2. Принятое решение и его обоснование

**Решение: параметры блоков создаются с СУФФИКСОМ ИНДЕКСА, число блоков задаётся настройкой, неприменённые блоки скрываются.**

Схема имён:

```
Вн<NN>Включение      — включение внутреннего блока NN
Вн<NN>Уставка        — уставка температуры
Вн<NN>ТПомещения     — температура помещения
Вн<NN>Режим          — текущий режим
Вн<NN>Вентилятор     — скорость вентилятора
Вн<NN>Ошибка         — ошибка блока
Вн<NN>Защита         — защита блока
```
где `<NN>` — двузначный индекс **01…66** (например `Вн01Включение`, `Вн66Защита`).

> **Почему индексы, а не «активен/скрыт» на одном наборе.** ТЗ прил. 1 ч. 2: «Для каждого блока **внутри экземпляра** предусмотрены собственные параметры». То есть блоки — часть **типа** ПБЭ, а не что-то внешнее. Индексный подход даёт каждому блоку полный набор параметров и при этом позволяет **одному типу** обслуживать и 55, и 62, и 66 блоков: неприменённые индексы скрываются.

### 5.3. (?) Риск, который нужно проверить в среде (допущение `D-90`)

**Число параметров ≈ 480…560 — рекордное для комплекта.** Возможные последствия, которые **нельзя проверить текстом**:

| Что может произойти | Почему | Что делать |
|---|---|---|
| Замедление открытия окон | сотни параметров на тип | допустимо; если критично — см. п. 5.4 |
| Ограничение числа параметров типа в версии 1.3.10 | предел не задокументирован в переданных материалах | **это первый вопрос к среде** (см. `сборка.md` шаг 0) |
| Неудобство настройки экземпляра | 66 блоков × 7 параметров | решается настройкой `КолВнутреннихБлоков` |

> **Честно:** я не могу утверждать, что версия 1.3.10.34633 без ограничений примет ~560 параметров одного типа. Это **проверяется только в среде**. Поэтому в инструкции по сборке этот пункт вынесен **первым шагом**, до основной работы.

### 5.4. Запасной вариант, если предел будет достигнут

Если среда не примет такое число параметров, применяется **разбиение по производителю**:

| Вариант | Что делается | Соответствие ТЗ |
|---|---|---|
| **A. Основной** (по ТЗ) | Один тип, индексы 01…66, неприменённые скрыты | ТЗ п. 1.1: «для каждой позиции Перечня разрабатывается **один** универсальный тип» |
| **B. Запасной** | Разбить параметры внутренних блоков на **два набора** по 33 индекса и переключать их настройкой `НаборБлоков` | (?) **Противоречит** п. 1.1 лишь внешне: тип остаётся **один**, меняется лишь способ хранения. Но требует согласования |
| **C. Крайний** | Вынести блоки в отдельный подчинённый объект, а ПБЭ № 5 оставить как «шапку» корпуса | ✘ **Противоречит** ТЗ: «Для каждого блока **внутри экземпляра** предусмотрены собственные параметры» |

**Рекомендация:** начинать с варианта **A**. Вариант **C** не применять — он прямо противоречит ТЗ. Вариант **B** предлагать ДИГАМ только если A технически невозможен.

## 9. Команды отдельному блоку — механизм выбора

**Требование ТЗ:** «**Команды отдельному блоку относятся к выбранному блоку.**»

### 9.1. Постановка задачи

Нельзя просто «записать уставку блоку» — надо сначала указать, **какому**. При 66 блоках это ключевой вопрос интерфейса.

### 9.2. Решение: индекс выбранного блока + строка ввода, меняющая своё назначение

**Механизм:**
1. В таблице (окно 5.7) каждая строка соответствует **своему** блоку — то есть у строки `NN` фиксированный индекс, и она пишет **прямо** в `Вн<NN>Уставка`, `Вн<NN>Режим`, `Вн<NN>Вентилятор`, `Вн<NN>Включение`. Это реализует требование «строки таблиц … выполняются в составе универсального ПБЭ».
2. Для **плана** (окно 5.5) и **трендов** (окна 5.8, 5.9) вводится **выбранный блок**: параметр `ВыбранныйБлок` (INT, 1…66). Метки на плане и тренды читают параметры **выбранного** блока.
3. Оператор выбирает блок **кликом по метке** на плане или **выбором строки** в таблице. Клик по метке устанавливает `ВыбранныйБлок` действием `Задать параметр`.
4. **Команды с панели тренда или с метки** (если предусмотрены) относятся к `ВыбранномуБлоку` — то есть к тому, который оператор выбрал.

### 9.3. Служебные параметры выбора

| Параметр | Тип | Описание |
|---|---|---|
| `ВыбранныйБлок` | INT | Индекс выбранного внутреннего блока (1…66) |
| `ВыбранныйБлокОбозначение` | STRING | Обозначение выбранного блока |
| `ВыбранныйБлокПомещение` | STRING | Помещение выбранного блока |
| `ВыбранныйБлокУставка` | REAL | Уставка выбранного блока |
| `ВыбранныйБлокТПомещения` | REAL | Температура помещения выбранного блока |
| `ВыбранныйБлокРежим` | INT | Режим выбранного блока |
| `ВыбранныйБлокВентилятор` | INT | Вентилятор выбранного блока |
| `ВыбранныйБлокВключение` | BOOL | Включение выбранного блока |
| `ВыбранныйБлокОшибка` | BOOL | Ошибка выбранного блока |
| `ВыбранныйБлокЗащита` | BOOL | Защита выбранного блока |

**Реализация «выбранного блока»:** программа **копирует** параметры блока с индексом `ВыбранныйБлок` в эти **девять** параметров — для **всех 66 индексов** (раздел 4 программы). Метки и тренды связаны с ними, а не с конкретным индексом. Это позволяет одному окну 5.5 отображать **любой** блок без дублирования графики.

| Параметр | Тип | Описание |
|---|---|---|
| `ЕстьВыбранныйБлок` | BOOL | Блок выбран |

> Текста состояния выбранного блока **отдельным параметром нет**: его формирует **конвертер** параметров `ВыбранныйБлокРежим` и `ВыбранныйБлокВентилятор` (см. `параметры.md` §3, §6.2).

## 10. Строки таблиц и метки блоков — в составе ПБЭ

ТЗ: «Строки таблиц и метки отдельных блоков **выполняются в составе универсального ПБЭ**».

**Следствие:** окна 5.2, 5.4, 5.5, 5.7 — это **одна строка/одна метка**, которая **размножается** столько раз, сколько блоков в экземпляре. То есть:
* окно 5.2 содержит **20 строк** (максимум наружных блоков) — неприменённые скрыты;
* окно 5.4 содержит **66 строк** (максимум внутренних) — неприменённые скрыты;
* окно 5.5 содержит **66 меток** — неприменённые скрыты;
* окно 5.7 содержит **66 строк ввода** — неприменённые скрыты.

**Скрытие строки:** входящая связь на свойство «Видимость» по условию «индекс ≤ `КолВнутреннихБлоков`» (через параметр-признак `Вн<NN>Применен`).

| Параметр | Тип | Описание |
|---|---|---|
| `Вн<NN>Применен` | BOOL | Выч: блок применён (индекс ≤ `КолВнутреннихБлоков`) |
| `Нар<NN>Применен` | BOOL | Выч: наружный блок применён |

> **Согласованность «Шапка ↔ Строка»** сохраняется: число колонок в 5.1 и 5.3 равно числу полей в 5.2 и 5.4 соответственно. См. §11.

## 12. Формирование значений для записи

ТЗ: «Применимые режимы, команды и обработка данных, **включая формирование значений для записи**, определяются вариантом оборудования и переданными ДИГАМ описаниями параметров и команд».

**Что это значит на практике.** Шлюзы LG, Electrolux и MDV могут принимать команды в разном виде:
* дискретные регистры (`Вкл` — бит);
* числовые коды режимов (у LG `1` = охлаждение, у другого производителя может быть иначе);
* скорость вентилятора как код или как процент.

**Реализация:**
1. В ПБЭ команды хранятся в **универсальном виде** (значения из списков §11.7).
2. **Формирование для записи** выполняется программой: универсальное значение → код, ожидаемый шлюзом конкретного производителя.
3. Соответствие задаётся **таблицей** в программе, зависящей от `Производитель`.

| Параметр | Тип | Описание |
|---|---|---|
| `Вн<NN>ВключениеЗапись` | INT | Значение для записи в шлюз (0/1) |
| `Вн<NN>РежимЗапись` | INT | Код режима для шлюза |
| `Вн<NN>ВентиляторЗапись` | INT | Код скорости для шлюза |
| `Вн<NN>УставкаЗапись` | REAL | Уставка для шлюза (например в 0,1 °C) |

> **Существенное ограничение, помечаемое честно.** Точные коды режимов для LG, Electrolux и MDV **не переданы** (допущение `D-91`). Поэтому в программе реализована **структура** преобразования с таблицей соответствия, заполненной **единообразными кодами** (0 Авто, 1 Охлаждение, 2 Нагрев, 3 Вентиляция, 4 Осушение). При получении описаний от ДИГАМ правится **только таблица**, логика не меняется.

## 17. Трудоёмкость (оценка)

| Работа | Оценка |
|---|---|
| **Параметры (~560)** | **10 ч** (в 2 раза больше, чем у любого другого ПБЭ) |
| Окна 5.1–5.4, 5.6, 5.7 (таблицы, с размножением строк) | 6 ч |
| Окно 5.5 «Метка блока» (66 меток) | 2 ч |
| Окна 5.8, 5.9 (тренды по выбранному блоку) | 1,5 ч |
| Программа ST (копирование выбранного блока, формирование для записи) | 6 ч |
| Настройка связей 66 × 4 пишущих элементов | **4 ч** |
| Проверка трёх экземпляров | 3 ч |
| **Итого** | **≈ 33 ч** |

> **Самая трудоёмкая часть — связи.** 66 строк × 4 пишущих элемента × 2 связи = **528 связей** только в окне 5.7. Это делается копированием строки с заменой индекса; **критично** не сбиться с индексации (см. `сборка.md`). Такую же работу даёт размножение строк в 5.2, 5.4 и меток в 5.5.
